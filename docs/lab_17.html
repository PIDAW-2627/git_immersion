lab 17 Eliminar commits de una rama

Objetivos

  • Aprender a eliminar los commits más recientes de una rama

El comando revert de la sección anterior es un comando potente que nos permite deshacer los efectos de cualquier commit del repositorio. Sin embargo, tanto el commit original como el commit que lo “deshace” son visibles en el historial de la rama (con el comando git log).

A menudo hacemos un commit y nos damos cuenta enseguida de que era un error. Estaría bien tener un comando para “retirar lo dicho” que nos permitiera hacer como si el commit incorrecto nunca hubiera existido. Ese comando incluso evitaría que el commit erróneo apareciera en el historial de git log. Sería como si el commit erróneo nunca hubiera ocurrido.

El comando reset

Ya hemos visto el comando reset y lo hemos usado para hacer que el área de preparación coincida con un commit dado (en el lab anterior usamos el commit HEAD).

Cuando se le pasa una referencia a un commit (es decir, un hash o un nombre de rama o etiqueta), el comando reset…

  1. Reescribe la rama actual para que apunte al commit indicado
  2. Opcionalmente, restablece el área de preparación para que coincida con el commit indicado
  3. Opcionalmente, restablece el directorio de trabajo para que coincida con el commit indicado

Revisa nuestro historial

Echemos un vistazo rápido a nuestro historial de commits.

Ejecuta:

git hist

Salida:

$ git hist
* b6120d7 2026-09-28 | Revert "Oops, we didn't want this commit" (HEAD -> main) [Jim Weirich]
* 936f37f 2026-09-28 | Oops, we didn't want this commit [Jim Weirich]
* 30bb300 2026-09-28 | Added a comment (tag: v1) [Jim Weirich]
* b883354 2026-09-28 | Added a default value (tag: v1-beta) [Jim Weirich]
* 15b00b7 2026-09-28 | Using ARGV [Jim Weirich]
* 36f205a 2026-09-28 | First Commit [Jim Weirich]

Vemos que tenemos un commit “Oops” y un commit “Revert Oops” como los dos últimos commits de esta rama. Vamos a eliminarlos usando reset.

Primero, marca esta rama

Pero antes de eliminar los commits, vamos a marcar el último commit con una etiqueta para poder encontrarlo de nuevo.

Ejecuta:

git tag oops

Haz reset a antes de Oops

Mirando el historial del log (arriba), vemos que el commit etiquetado como ‘v1’ es el commit justo anterior al commit erróneo. Vamos a hacer reset de la rama a ese punto. Como ese commit está etiquetado, podemos usar el nombre de la etiqueta en el comando reset (si no estuviera etiquetado, podríamos usar simplemente el valor hash).

Ejecuta:

git reset --hard v1
git hist

Salida:

$ git reset --hard v1
HEAD is now at 30bb300 Added a comment
$ git hist
* 30bb300 2026-09-28 | Added a comment (HEAD -> main, tag: v1) [Jim Weirich]
* b883354 2026-09-28 | Added a default value (tag: v1-beta) [Jim Weirich]
* 15b00b7 2026-09-28 | Using ARGV [Jim Weirich]
* 36f205a 2026-09-28 | First Commit [Jim Weirich]

Nuestra rama main apunta ahora al commit v1, y los commits Oops y Revert Oops ya no están en la rama. El parámetro --hard indica que el directorio de trabajo debe actualizarse para ser coherente con la nueva cabeza de la rama.

Nunca se pierde nada

Pero ¿qué ha pasado con los commits erróneos? Resulta que los commits siguen en el repositorio. De hecho, todavía podemos hacer referencia a ellos. Recuerda que al principio de este lab etiquetamos el commit de reversión con la etiqueta “oops”. Veamos todos los commits.

Ejecuta:

git hist --all

Salida:

$ git hist --all
* b6120d7 2026-09-28 | Revert "Oops, we didn't want this commit" (tag: oops) [Jim Weirich]
* 936f37f 2026-09-28 | Oops, we didn't want this commit [Jim Weirich]
* 30bb300 2026-09-28 | Added a comment (HEAD -> main, tag: v1) [Jim Weirich]
* b883354 2026-09-28 | Added a default value (tag: v1-beta) [Jim Weirich]
* 15b00b7 2026-09-28 | Using ARGV [Jim Weirich]
* 36f205a 2026-09-28 | First Commit [Jim Weirich]

Aquí vemos que los commits erróneos no han desaparecido. Siguen en el repositorio. Lo que pasa es que ya no aparecen en la rama main. Si no los hubiéramos etiquetado, seguirían en el repositorio, pero no habría forma de referenciarlos salvo usando sus hashes. Los commits sin referencias permanecen en el repositorio hasta que el sistema ejecuta el recolector de basura (garbage collection).

Peligros de reset

Hacer reset en ramas locales suele ser seguro. Normalmente cualquier “accidente” se puede arreglar volviendo a hacer reset al commit deseado.

Sin embargo, si la rama se comparte en repositorios remotos, hacer reset puede confundir a otros usuarios que comparten esa rama.
