h1. Preparar y hacer commit

p. Tener un paso de preparación separado en git encaja con la filosofía de
no molestarte hasta que necesites ocuparte del control de versiones.
Puedes seguir haciendo cambios en tu directorio de trabajo y, en el
momento en que quieras interactuar con el control de versiones, git te permite
registrar tus cambios en commits pequeños que reflejan exactamente lo que
has hecho.

p. Por ejemplo, supón que has editado tres archivos (@a.rb@, @b.rb@ y
@c.rb@). Ahora quieres hacer commit de todos los cambios, pero quieres que
los cambios de @a.rb@ y @b.rb@ formen un solo commit, mientras que los cambios
de @c.rb@ no tienen relación lógica con los dos primeros archivos y deberían
ir en un commit aparte.

p. Podrías hacer lo siguiente:

pre(instructions).
git add a.rb
git add b.rb
git commit -m "Changes for a and b"

pre(instructions).
git add c.rb
git commit -m "Unrelated change to c"

p. Al separar la preparación del commit, puedes ajustar con
facilidad qué entra en cada commit.

h1. Cambios, no archivos

h2. Objetivos

* Aprender que git trabaja con cambios, no con archivos.

p. La mayoría de los sistemas de control de versiones trabajan con archivos. Añades un archivo
al control de versiones y el sistema registra los cambios en ese archivo a partir de
ese momento.

p. Git se centra en los cambios de un archivo, más que en el archivo en sí.
Cuando escribes @git add file@, no le estás diciendo a git que añada el archivo
al repositorio. Lo que le dices es que tome nota del
estado actual de ese archivo para incluirlo más adelante en un commit.

p. En este lab intentaremos explorar esa diferencia.

h2. Primer cambio: permitir un nombre por defecto

p. Modifica el programa "Hello, World" para que tenga un valor por defecto si no se
le pasa ningún argumento en la línea de comandos.

File: hello.rb
name = ARGV.first || "World"

puts "Hello, #{name}!"
EOF

h2. Añade este cambio

p. Ahora añade este cambio al área de preparación (staging) de git.

Execute:
git add hello.rb

h2. Segundo cambio: añadir un comentario

p. Ahora añade un comentario al programa "Hello, World".

File: hello.rb
# Default is "World"
name = ARGV.first || "World"

puts "Hello, #{name}!"
EOF

h2. Comprueba el estado actual

Execute:
!git status
=status

p. Deberías ver...

Output:
=status
EOF

p. Fíjate en que @hello.rb@ aparece dos veces en el estado. El primer
cambio (añadir un valor por defecto) está preparado y listo para el commit. El
segundo cambio (añadir un comentario) no está preparado. Si hicieras commit
ahora mismo, el comentario no se guardaría en el repositorio.

p. Vamos a probarlo.

h2. Hacer commit

p. Haz commit del cambio preparado (el valor por defecto) y vuelve a comprobar
el estado.

Execute:
git commit -m "Added a default value"
=commit
git status
=status2

p. Deberías ver...

Output:
=commit
=status2
EOF

p. El comando status te indica que @hello.rb@ tiene cambios sin registrar,
pero ya no está en el área de preparación.

h2. Añade el segundo cambio

p. Ahora añade el segundo cambio al área de preparación y ejecuta git status.

Execute:
git add .
!git status
=status3

p(note). *Nota:* Hemos usado el directorio actual ('.') como el
archivo que añadir. Es un atajo muy cómodo para añadir todos
los cambios de los archivos del directorio actual y de sus subdirectorios. Pero,
como lo añade todo, es _muy_ buena idea comprobar el estado
antes de hacer un <tt>add .</tt>, para asegurarte de que no añades ningún
archivo que no querías.

p(note). Quería que conocieras el truco de "add .", pero en el resto del
tutorial seguiremos añadiendo los archivos de forma explícita, por
seguridad.

p. Deberías ver...

Output:
=status3
EOF

p. Ahora el segundo cambio está preparado y listo para el commit.

h2. Haz commit del segundo cambio

Execute:
git commit -m "Added a comment"

h2. Historial en una línea

p. Tienes mucho control sobre lo que muestra exactamente el comando @log@.
A mí me gusta el formato de una sola línea:

Execute:
git log --pretty=oneline
=oneline

p. Deberías ver...

Output:
=oneline
EOF

h2. Controlar qué entradas se muestran

p. Hay muchas opciones para seleccionar qué entradas se
muestran en el log. Prueba con las siguientes opciones:

pre(instructions).
git log --pretty=oneline --max-count=2
git log --pretty=oneline --since='5 minutes ago'
git log --pretty=oneline --until='5 minutes ago'
git log --pretty=oneline --author=<your name>
git log --pretty=oneline --all

p. Consulta man git-log para ver todos los detalles.

h2. Rizando el rizo

p. Esto es lo que uso yo para revisar los cambios hechos en la última semana.
Añado @--author=jim@ si solo quiero ver los cambios que he hecho yo.

pre(instructions).
git log --all --pretty=format:'%h %cd %s (%an)' --since='7 days ago'

h2. El formato de log definitivo

p. Con el tiempo, he decidido que me gusta el siguiente formato de log para
la mayor parte de mi trabajo.

Execute:
git log --pretty=format:'%h %ad | %s%d [%an]' --graph --date=short
=ultimate

Tiene este aspecto:

Output:
=ultimate
EOF

p. Veámoslo en detalle:

* @--pretty=format:"..."@ define el formato de la salida.
* @%h@ es el hash abreviado del commit
* @%ad@ es la fecha del autor
* @%s@ es el comentario
* @%d@ son las decoraciones de ese commit (p. ej., cabezas de rama o etiquetas)
* @%an@ es el nombre del autor
* @--graph@ indica a git que muestre el árbol de commits como un gráfico ASCII
* @--date=short@ mantiene el formato de fecha bonito y corto

p. Es mucho que escribir cada vez que quieras ver el log.
Por suerte, en el próximo lab aprenderemos a usar los alias de git.

h2. Otras herramientas

p. Tanto <code>gitx</code> (para Mac) como <code>gitk</code> (cualquier
plataforma) son útiles para explorar el historial del log.

h1. Alias

h2. Objetivos

* Aprender a configurar alias y atajos para los comandos de git

h2. Alias habituales

p. @git status@, @git add@, @git commit@ y @git checkout@ son comandos
tan habituales que resulta útil tener abreviaturas para ellos.

p. Añade lo siguiente al archivo .gitconfig de tu directorio $HOME.

file: .gitconfig
[alias]
  co = checkout
  ci = commit
  st = status
  br = branch
  hist = log --pretty=format:'%h %ad | %s%d [%an]' --graph --date=short
  type = cat-file -t
  dump = cat-file -p
EOF

p. Ya hemos visto los comandos commit y status. Y acabamos de
ver el comando @log@ en el lab anterior. El comando @checkout@
llegará pronto.

p. Con estos alias definidos en el archivo @.gitconfig@ puedes escribir
@git co@ donde antes tenías que escribir @git checkout@. Lo mismo
con @git st@ para @git status@ y @git ci@ para @git commit@. Y lo
mejor de todo: @git hist@ te permitirá evitar el larguísimo
comando @log@.

p. Adelante, prueba los nuevos comandos.

h2. Define el alias @hist@ en tu archivo @.gitconfig@

p. En general, seguiré escribiendo el comando completo en
estas instrucciones. La única excepción es que usaré el alias @hist@
definido arriba siempre que necesitemos ver la salida de git log. Asegúrate
de tener configurado un alias @hist@ en tu archivo @.gitconfig@ antes de
continuar si quieres seguir el tutorial paso a paso.

h2. @Type@ y @Dump@

p. Hemos añadido algunos alias para comandos que aún no hemos visto. El
comando @git branch@ llegará pronto. Y el comando @git cat-file@
es útil para explorar git, como veremos dentro de un
rato.

h2. Alias de la shell (opcional)

p(note). *Nota:* Esta sección es para quienes usan una shell tipo posix.
Si usas Windows u otra shell no posix, puedes saltar directamente al
siguiente lab.

p. Si tu shell admite alias o atajos, también puedes añadir
alias a ese nivel. Estos son los que uso yo:

file: .profile
alias gs='git status '
alias ga='git add '
alias gb='git branch '
alias gc='git commit'
alias gd='git diff'
alias gco='git checkout '
alias gk='gitk --all&'
alias gx='gitx --all'

alias got='git '
alias get='git '
EOF

p. La abreviatura @gco@ para @git checkout@ es especialmente práctica. Me
permite escribir:

pre(instructions). gco <branch>

p. para cambiar a una rama concreta.

p. Y sí, escribo mal @git@ como @get@ o @got@ con la frecuencia suficiente
como para crearles alias.

h2. Deshacer commits

p. A veces te das cuenta de que un cambio que ya has confirmado
no era correcto y quieres deshacer ese commit. Hay varias formas
de resolver este problema, y la que vamos a usar en este lab
es siempre segura.

invierte los cambios no deseados.

p. Pero ¿qué ha pasado con los commits erróneos? Resulta que los
commits siguen en el repositorio. De hecho, todavía podemos hacer
referencia a ellos. Recuerda que al principio de este lab etiquetamos el

EOF

p. Aquí vemos que los commits erróneos no han desaparecido. Siguen

la rama main. Si no los hubiéramos etiquetado, seguirían en
el repositorio, pero no habría forma de referenciarlos salvo
usando sus hashes. Los commits sin referencias permanecen en el
repositorio hasta que el sistema ejecuta el recolector de basura (garbage collection).

h2. Peligros de reset

p. Hacer reset en ramas locales suele ser seguro. Normalmente cualquier
"accidente" se puede arreglar volviendo a hacer reset al
commit deseado.

p. Sin embargo, si la rama se comparte en repositorios remotos, hacer reset
puede confundir a otros usuarios que comparten esa rama.

podremos mostrar el comando rebase sin preocuparnos por
los conflictos.

Execute:
git checkout main
git hist
=log

Output:
=log
EOF

p. El commit 'Added README' es el inmediatamente anterior al
modo interactivo conflictivo.  Restableceremos la rama main al
commit 'Added README'.

Set: hash=hash_for("Added README")

=log2

h1. Hacer rebase

h2. Objetivos

* Usar el comando rebase en lugar del comando merge.

p. Bien, hemos vuelto a un momento anterior a la primera fusión y queremos llevar
los cambios de main a nuestra rama greet.

p. Esta vez usaremos el comando rebase en lugar del comando merge
para traer los cambios de la rama main.

Execute:
git checkout greet
git rebase main
git hist
=log

Output:
$ git checkout greet
Switched to branch 'greet'
$
$ git rebase main
First, rewinding head to replay your work on top of it...
Applying: added Greeter class
Applying: hello uses Greeter
Applying: updated Rakefile
$
=log
EOF

h2. Merge VS rebase

p. El resultado final del rebase es muy parecido al de la fusión.  La
rama greet contiene ahora todos sus cambios, además de todos los
cambios de la rama main.  Sin embargo, el árbol de commits es bastante
distinto.  El árbol de commits de la rama greet se ha reescrito de forma
que la rama main forma parte del historial de commits.  Así
la cadena de commits queda lineal y es mucho más fácil de leer.

h2. ¿Cuándo hacer rebase y cuándo fusionar?

p. No uses rebase...

# Si la rama es pública y está compartida con otras personas.  Reescribir ramas compartidas públicamente suele causar problemas al resto del equipo.
# Cuando el historial _exacto_ de la rama de commits es importante (ya que rebase reescribe el historial de commits).

p. Siguiendo estas pautas, yo suelo usar rebase para ramas locales de
vida corta y fusionar para las ramas del repositorio público.

h1. Fusionar de vuelta en main

h2. Objetivos

h2. Fusionar greet en main

Execute:
git checkout main
git merge greet
=merge

Output:
$ git checkout main

$
=merge
EOF

p. Como la cabeza de main es un ancestro directo de la cabeza de la

hacer fast-forward, el puntero de la rama simplemente avanza para apuntar
al mismo commit que la rama greet.

p. En una fusión fast-forward nunca habrá conflictos.

=log
EOF
